# ADR-0004: M4 Tool Lab — browser-tier parity strategy

Date: 2026-05-10
Status: Accepted

## Context

M4 ports the VLM-DENTAL agent tools (`dental_agent/tools/*.py`) to TypeScript for
client-side execution (plan §9 browser tier). Python references use PIL and OpenCV,
whose exact numeric behavior must be replicated or the parity tests are meaningless.
Goldens are generated by `scripts/generate_m4_goldens.py`, which imports the *real*
Python tool functions from `../VLM-DENTAL` and snapshots outputs to
`fixtures/goldens/m4_tools.json`.

## Decisions

### 1. PIL `ImageEnhance.Contrast` is replicated bit-exact by probing Pillow's source+behavior

The port (`enhanceContrast`) is **not** a naive `mean + (v-mean)*factor` float blend.
Verified against Pillow 12.3 source and empirical probes:

1. Convert image to `L` using the integer Rec.601 formula, **round-to-nearest**
   (`(19595R + 38470G + 7471B + 32768) >> 16`; probe `(100,150,200) → 141`, not 140).
2. Degenerate mean = `int(mean(L) + 0.5)` (an *integer*, not a float).
3. `enhance = Image.blend(degenerate, image, factor)` whose C implementation
   **truncates toward zero** after clamping. Golden `contrast_tie` locks this:
   `mean=128, factor=1.25 → 50.5 → 50` (round-half-even would give 50, but
   `205.5 → 205` rules out banker's rounding; truncation matches both).

### 2. `cv2.bilateralFilter` port is bit-exact (not an approximation)

Four candidate formulations were fit against the golden; only one achieved
mean abs diff **0.0** (max 0):

- range weight `exp(-(L1_color)² / (2·σColor²))` where `L1 = |Δr|+|Δg|+|Δb|`
  (city-block, then **squared** — confirmed in OpenCV's `expLUT` construction:
  `exp(val² · gauss_color_coeff)` with `val` = L1 delta),
- **circular** spatial kernel (`r ≤ radius`, not the full square),
- `BORDER_REFLECT_101` border (not replicate).

Naive L2-Gaussian range weights differ by ~24/255 mean on the noise probe — far
outside tolerance. The port uses lookup tables (766-entry L1 table, spatial table)
so a full-resolution pass stays interactive.

### 3. `cv2.medianBlur` port: per-channel median, odd kernel, `BORDER_REPLICATE`

`ksize = round(3 + strength·10)` forced odd; verified exact for all 64 golden pixels.

### 4. Windowing truncates, contrast truncates, PIL `L` rounding differs per tool

`tool_window_level` maps via `np.astype(np.uint8)` which **truncates**
(`183.6 → 183`, `56.1 → 56`). Golden vectors cover all four presets, a custom
center/width override, and the unknown-preset fallback (→ `bone`).

### 5. Browser-tier scope: 7 of 8 registry tools; `locate_tooth` stays runtime-only

`locate_tooth` runs YOLO inference — model weights and inference cannot run in the
browser tier (plan §9). The Tool Lab UI states this explicitly and points at Trace
Explorer for real outputs. The 154 parity renders in `docs/images/` are not yet
ported (optional backlog).

### 6. Performance vs. fidelity in the UI

`denoise` previews at ≤720px width (kernel is O(w·h·k²)); the JSON panel reports the
actual kernel parameters (`ksize`, or `d`/`sigmaColor`/`sigmaSpace`) and the
`preview_scale` so nothing is implied about full-resolution behavior. All other tools
run at full source resolution.

### 7. Known risk: `round(x, 1)` tie behavior in `nudge_crop`

Python uses round-half-even; the TS port uses `Math.round(v*10)/10`
(half-away-from-zero). No tie appears in the goldens; a divergence would require an
exact `.05` fractional coordinate. Documented, not mitigated.

## Consequences

- `tests/m4-tools.test.ts` asserts **exact** equality (not tolerance) for contrast,
  windowing, median, bilateral, geometry, contralateral, and FDI helpers — 16 tests.
- Any PIL/OpenCV upgrade in VLM-DENTAL that changes numerics will fail the golden
  regeneration diff and force an explicit review.
- Total suite: 72 tests.
